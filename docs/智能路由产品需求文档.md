# 智能路由产品需求文档

版本：v0.2

## 1. 文档目的

本文描述智能路由服务应提供的产品能力和业务规则，不绑定任何具体框架、代码结构、模型供应商或部署方式。本文用于产品、业务、测试和研发对齐需求范围、核心流程、接口语义和验收标准。

## 2. 背景

智能助手入口需要面对大量业务场景。用户可能一次表达一个诉求，也可能一次表达多个诉求；可能直接提供完整信息，也可能需要多轮补充。随着业务能力增加，如果所有业务规则在每次请求中同时参与判断，会造成识别干扰、响应不稳定、成本升高和问题难定位。

因此，需要一个统一的智能路由能力，负责识别用户意图、拆分任务、收集任务所需信息、管理任务上下文，并在任务满足办理条件后交给后续业务执行系统。

## 3. 目标

1. 支持大量业务能力的统一接入和可发现。
2. 支持单意图、多意图、多轮补充、任务取消、任务完成和任务切换。
3. 支持推荐任务卡片，由用户决定接受、部分接受或拒绝。
4. 支持任务完成后及时释放临时上下文，避免长期占用会话内存。
5. 支持多人在线使用，同一会话只能绑定一个用户。
6. 支持流式和非流式两类响应方式，最终业务语义保持一致。
7. 提供可观测链路，便于定位识别、补充信息、任务推进和上下文释放问题。

## 4. 范围

### 4.1 范围内

1. 用户自然语言请求的意图识别。
2. 多意图请求拆分为多个独立任务。
3. 当前任务所需信息的收集与补充。
4. 推荐任务卡片的接受、部分接受、拒绝和忽略。
5. 任务状态管理和串行调度。
6. 会话用户绑定和空闲过期清理。
7. 任务达到办理条件后的交接。
8. 执行系统返回结果后的透传或归档。
9. 调试链路和关键状态可观测。

### 4.2 范围外

1. 具体业务系统内部如何办理交易、缴费或查询。
2. 具体大模型、框架或编排引擎选型。
3. 前端页面视觉设计细节。
4. 生产环境部署、扩缩容、告警和运维平台建设。

## 5. 职责边界

智能路由能力由服务主体、业务能力配置和下游执行系统共同完成。本文中的“系统”并不表示所有能力都由服务主体独立实现；不同职责应按以下边界拆分。

本文后续将业务能力配置统称为 skills。skills 是本服务的主要下游协作主体之一，负责声明业务知识、意图边界、所需信息和执行契约。服务主体不预置具体业务能力，而是基于 skills 提供的内容驱动意图识别、任务规划、信息收集和交接执行。

### 5.1 服务主体职责

服务主体负责通用路由和任务治理能力：

1. 接收用户输入、推荐任务、当前展示态和前端透传信息。
2. 管理用户会话、用户绑定、空闲过期和任务运行态。
3. 基于业务能力摘要完成意图识别和多意图拆分。
4. 创建任务队列，选择当前任务，并按串行方式推进任务。
5. 在当前任务范围内组织信息收集、状态判断、澄清和交接。
6. 控制临时上下文加载、隔离、释放和调试观测。
7. 校验任务、会话、用户和响应协议的通用一致性。
8. 在任务达到办理条件后，按业务能力声明的契约交给下游执行系统。

服务主体不负责定义具体业务规则，不内置具体业务意图、槽位含义、业务话术、业务接口含义或业务办理逻辑。

### 5.2 Skills 职责

Skills 用于承载具体业务知识和办理要求。每个 skill 应配合提供：

1. 业务能力名称和摘要说明，用于被系统发现和路由。
2. 唯一业务意图标识。
3. 业务支持范围和不支持范围。
4. 必填信息项、可选信息项和字段含义。
5. 多轮补充信息时的抽取规则和澄清规则。
6. 面向用户的必要追问口径。
7. 是否需要外部执行，以及执行所需契约。
8. 长规则、名单、枚举、案例、接口说明等可按需引用的资料。

Skills 应避免承载多个独立业务意图。如果多个意图共享资料，应拆分为多个 skill，并复用公共资料或公共执行契约。

服务主体对 skills 的使用应遵循渐进式原则：

1. 首轮识别只使用 skill 的摘要信息，避免一次性加载全部业务规则。
2. 命中某个任务后，只加载当前任务对应 skill 的详细规则。
3. 长规则、枚举、接口说明等资料只在当前 skill 授权且当前任务需要时加载。
4. 任务结束后，服务主体应释放该任务关联的 skill 详细内容和临时资料引用。
5. 服务主体只能校验 skill 声明的一致性，不能自行补充或覆盖 skill 的业务规则。

### 5.3 下游执行系统职责

下游执行系统负责真实业务办理或查询：

1. 接收已确认的业务意图、已收集信息和必要透传参数。
2. 执行业务系统调用、校验、交易、查询或状态变更。
3. 返回业务执行结果、失败原因或后续交互要求。
4. 保证业务执行的权限、风控、幂等和审计。

智能路由服务不应替代下游执行业务校验，也不应改写下游返回的业务私有结构，除非双方契约明确要求。

## 6. 核心概念

### 6.1 用户会话

用户会话表示一次用户与助手的连续交互边界。会话用于绑定用户、保存当前未完成任务的轻量状态，并在空闲超时后释放。

规则：

1. 一个会话只能绑定一个用户。
2. 不同用户不能复用同一个会话状态。
3. 会话默认空闲 30 分钟过期。
4. 会话过期后，未完成任务、已收集信息和临时上下文都应清除。
5. 过期后再次使用相同会话标识，应按新会话处理。

### 6.2 业务能力

业务能力是可被智能路由识别和调度的独立业务单元，在系统协作中通常由 skill 承载。每个业务能力应具备：

1. 可识别的名称和简要说明。
2. 唯一的业务意图标识。
3. 完成该业务所需的信息项。
4. 业务边界和不支持范围说明。
5. 必要时的执行契约或外部资料引用。

规则：

1. 一个业务能力只承载一个可派发业务意图。
2. 一个业务意图只能被一个明确业务能力承载。
3. 不允许把多个独立意图混在一个业务能力中处理。
4. 业务规则、槽位含义、追问口径和执行语义应由业务能力自身声明。

### 6.3 任务

任务是用户某个明确业务诉求的运行实例。

任务至少包含：

1. 任务标识。
2. 业务意图。
3. 任务状态。
4. 已收集信息。
5. 用户原始表达片段。
6. 当前是否可交接办理。

规则：

1. 一个任务只对应一个业务意图。
2. 多个任务可以存在于同一会话中。
3. 多任务必须串行处理，同一时刻只有一个当前任务。
4. 当前任务未完成前，不得并行推进其他任务的补充信息或办理流程。

## 7. 用户流程

### 7.1 单意图流程

当用户表达一个业务诉求时：

1. 系统识别用户意图。
2. 系统创建一个任务。
3. 系统判断任务所需信息是否齐全。
4. 信息不齐时，系统向用户发起补充询问。
5. 用户补充信息后，系统合并到当前任务。
6. 信息齐全时，任务进入可交接办理状态。
7. 后续执行系统完成任务后，系统释放该任务状态。

示例：

用户：“我要办理某项业务。”  
系统：识别业务意图，发现缺少必要信息，询问用户补充。

### 7.2 多意图流程

当用户一次表达多个独立诉求时：

1. 系统识别所有独立业务意图。
2. 系统为每个意图创建独立任务。
3. 系统按用户表达顺序或业务规则确定任务顺序。
4. 系统选择第一个任务作为当前任务。
5. 当前任务完成后，系统切换到下一个任务。
6. 全部任务完成后，会话中不再保留任务运行态。

规则：

1. 多个任务的已收集信息不得互相串用。
2. 当前任务的补充信息不得写入非当前任务。
3. 用户明确指定“第一笔、第二个、刚才那个”等顺序时，应按任务队列定位。
4. 无法判断补充信息归属时，应发起澄清。

### 7.3 多轮补充信息

当任务缺少必要信息时：

1. 系统应明确提示用户补充缺失信息。
2. 用户下一轮提供的信息只应合并到当前任务。
3. 用户提供多个信息项时，应一次性提取并合并。
4. 用户修改已提供信息时，应以用户明确的新表达为准。
5. 用户表达取消时，应取消对应任务或全部任务。

### 7.4 推荐任务卡片

前端或上游系统可以向用户展示推荐任务卡片，并在用户回复时将推荐任务列表随请求传入。

系统应支持：

1. 用户接受全部推荐任务。
2. 用户只接受部分推荐任务。
3. 用户明确拒绝推荐任务。
4. 用户不选择推荐任务，而表达其他诉求。
5. 用户没有对推荐任务做出明确选择。

规则：

1. 推荐任务只影响当前轮判断。
2. 用户明确接受推荐任务时，系统应基于被接受的推荐创建任务。
3. 用户只接受部分推荐时，只创建被接受任务。
4. 用户明确拒绝推荐任务时，不应创建推荐任务。
5. 用户拒绝推荐后又表达其他诉求时，应按用户真实诉求处理。
6. 用户不接受推荐而表达其他诉求时，应忽略推荐任务，按用户真实诉求处理。
7. 用户未做选择时，推荐任务不得污染后续会话状态。
8. 推荐任务的具体可识别描述、业务意图和所需信息仍由业务能力配置配合提供。

示例：

推荐任务：任务 A、任务 B。  
用户：“全部办理。”  
系统：创建任务 A 和任务 B，并串行处理。

用户：“只办理任务 A。”  
系统：只创建任务 A。

用户：“不用了。”  
系统：不创建推荐任务，并保持当前会话可继续接收新输入。

用户：“我想办理任务 C。”  
系统：忽略推荐任务，识别并处理任务 C。

### 7.5 任务完成

当后续业务执行系统完成某个任务时：

1. 系统接收任务完成信号。
2. 系统确认该任务属于当前用户会话。
3. 系统更新任务状态。
4. 系统释放该任务相关临时上下文。
5. 如果还有等待任务，系统切换到下一个任务。
6. 如果没有等待任务，系统清空当前任务队列。

## 8. 状态要求

任务状态至少包括：

1. 处理中。
2. 等待用户补充信息。
3. 信息齐全，等待交接办理。
4. 等待外部执行完成。
5. 已完成。
6. 已取消。
7. 已失败。

状态规则：

1. 缺少必要信息时，任务不能进入可交接办理状态。
2. 信息齐全后，任务应进入可交接办理状态。
3. 已完成、已取消、已失败任务不再接收补充信息。
4. 已结束任务应从运行态任务队列中移除。
5. 多任务场景下，当前任务结束后才能推进下一个任务。

## 9. 接口能力要求

### 9.1 消息入口

消息入口用于接收用户输入并返回当前路由结果。

请求能力：

1. 接收会话标识。
2. 接收用户标识。
3. 接收用户自然语言输入。
4. 接收是否流式响应。
5. 接收是否输出调试信息。
6. 接收执行模式。
7. 接收推荐任务列表。
8. 接收当前展示态和前端透传变量。

响应能力：

1. 返回识别到的业务意图。
2. 返回当前任务状态。
3. 返回已收集信息。
4. 返回任务列表。
5. 返回当前任务。
6. 返回面向用户的提示信息。
7. 返回错误原因。
8. 流式响应时可分阶段返回事件。

### 9.2 任务完成入口

任务完成入口用于接收外部执行系统的任务完成结果。

请求能力：

1. 接收会话标识。
2. 接收用户标识。
3. 接收任务标识。
4. 接收完成信号。

响应能力：

1. 返回任务完成结果。
2. 返回下一个待处理任务。
3. 返回任务队列变化。
4. 返回上下文释放结果。

### 9.3 探活能力

系统应提供基础存活检查和就绪检查，用于判断服务是否可接收请求。

## 10. 执行交接要求

当任务达到可办理条件时，系统可以根据业务能力声明的执行契约调用外部执行系统。

要求：

1. 模型只负责识别意图和收集业务所需信息。
2. 外部执行所需的非业务信息应由前端、会话或配置提供。
3. 外部执行地址、鉴权、参数映射和返回格式应由 skill 或其关联契约声明。
4. 系统不应让模型自由拼接执行地址、请求头或请求体。
5. 外部执行返回内容可以按契约透传给前端。
6. 系统不应理解或改写外部执行结果中的业务私有结构，除非契约明确要求。

## 11. 安全与隐私要求

1. 用户标识和会话标识不得作为业务意图判断依据。
2. 用户标识和会话标识不得交给模型生成或改写。
3. 不得跨用户读取或复用任务状态。
4. 推荐任务、当前展示态和前端透传变量只影响当前请求。
5. 临时上下文不得长期保存业务规则正文。
6. 调试信息在生产环境应可关闭。
7. 错误信息不得泄露密钥、鉴权信息或内部系统敏感地址。

## 12. 可观测性要求

开启调试时，应能观察：

1. 请求进入。
2. 会话绑定和过期判断。
3. 可用业务能力摘要。
4. 意图识别结果。
5. 多任务拆分结果。
6. 当前任务选择。
7. 任务信息收集结果。
8. 任务状态变化。
9. 推荐任务是否被接受、部分接受、拒绝或忽略。
10. 外部执行是否触发。
11. 任务完成和上下文释放。
12. 错误来源和错误分类。

## 13. 异常处理

系统应处理以下异常：

1. 未识别到可处理意图。
2. 多个候选意图无法明确区分。
3. 必要信息缺失。
4. 补充信息归属不明确。
5. 用户取消任务。
6. 会话被其他用户复用。
7. 会话已过期。
8. 外部执行系统超时或失败。
9. 模型返回格式不符合要求。
10. 推荐任务格式不合法。
11. 用户明确拒绝推荐任务。

异常响应应包含稳定错误分类和可理解提示，不应导致服务进程不可用。

## 14. 验收标准

### 14.1 单意图

1. 用户表达单个诉求时，系统能创建一个任务。
2. 信息不足时，系统能提示补充。
3. 用户补充信息后，系统能合并到同一任务。
4. 信息齐全后，系统能进入可交接办理状态。

### 14.2 多意图

1. 用户一次表达多个诉求时，系统能创建多个任务。
2. 每个任务只包含一个业务意图。
3. 多任务按顺序串行处理。
4. 第一个任务完成后，系统能推进下一个任务。
5. 多任务之间信息不串用。

### 14.3 推荐任务

1. 用户接受全部推荐任务时，系统创建全部被推荐任务。
2. 用户接受部分推荐任务时，系统只创建被接受任务。
3. 用户明确拒绝推荐任务时，系统不创建推荐任务。
4. 用户拒绝推荐后表达其他诉求时，系统按其他诉求处理。
5. 用户表达其他诉求时，系统忽略推荐任务。
6. 用户未选择推荐任务时，推荐任务不影响后续请求。

### 14.4 会话

1. 同一会话只能绑定一个用户。
2. 会话空闲 30 分钟后过期。
3. 过期后不继承历史任务状态。
4. 一个会话的过期不影响其他会话。

### 14.5 交接执行

1. 任务信息齐全且模式允许时，系统能交给外部执行系统。
2. 外部执行结果能返回给前端。
3. 外部执行失败时，系统返回明确失败状态。
4. 外部执行不影响其他等待任务。

### 14.6 可观测性

1. 调试模式能展示关键阶段。
2. 非调试模式不输出冗余内部信息。
3. 流式和非流式最终业务结果一致。
